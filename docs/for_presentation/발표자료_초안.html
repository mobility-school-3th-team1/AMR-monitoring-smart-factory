1. 프로젝트 전체 개요

1.1 프로젝트 주제 및 선정 배경

주제

고중량 배터리 팩 조립 공장에서 운용되는 AMR(자율 이동 로봇)의 위치, 상태, 환경, 충전, 작업 이력을 실시간 통합 관제하는 웹 시스템

선정 배경

  • 로봇 친화(RF) 제조 확산에도 운영 효율은 정체되는 현장
  • AMR 도입 후 MES/WMS 연동 미비로 “스스로 움직이는 카트” 수준에 머무는 사례
  • 센서 교란, 경로 이탈, 데드락 등 안전, 소프트웨어 리스크 증가
  • 분산 데이터를 통합해 의사결정, 선제 대응이 필요한 관제 수요

기획 의도

  • 단순 위치 표시를 넘어 안전(비상 정지), 환경 위험 감시, 운영 인사이트를 한 화면에 제공
  • 실제 설비 대신 Node-RED DAS 시뮬레이션으로 개발, 시연 가능한 구조 확보
  • 설계 문서 선행(Design-first)과 AI 보조 개발로 제한된 기간 내 멀티 스택 병행

메인 대시보드

공장 전체를 한눈에 보고, 지금 어디서 무엇이 일어나는지를 즉시 파악할 수 있습니다.

의도와 목적

AMR, 환경, 알람, 작업 로그가 여러 화면과 시스템에 흩어져 있으면 대응이 늦어집니다. 이 화면은 통합 관제의 시작점으로, 운영자가 스크롤 없이 한 화면에서 현장 상황의 전체 그림을 얻도록 설계했습니다.

고객이 얻는 것

  • 공장 평면도 위에서 AMR 위치, 이동, 상태(운행, 대기, 충전, 오류)를 색으로 구분해 어느 구역에 문제가 있는지 바로 알 수 있습니다.
  • 구역별 온도, 습도, 미세먼지를 함께 보며 환경 이상과 로봇 이상을 한 맥락에서 판단할 수 있습니다.
  • 운영, 대기, 충전, 에러 대수와 미해결 건수를 카드로 확인해, 우선 대응할 대상을 빠르게 고를 수 있습니다.
  • 충돌, 경로 이탈, 고장 등 중요 알람과 작업 로그를 실시간으로 받아, 사고 확대 전에 조치를 시작할 수 있습니다.

목표: 여러 창을 돌아다니지 않고도, 10초 안에 공장 물류와 안전 상태의 1차 판단을 끝낸다.

핵심 기능: 평면도, 환경 현황, 상태 요약 카드, 실시간 알람, 작업 로그 | 구현: FE DashboardView, BE GET /dashboard/summary 등

4.5 페이지별 기능

SCR-02

AMR 전체 관리

전체 AMR을 목록, 통계, 추이로 묶어 보고, 어느 장비, 어느 시기에 운영이 흔들리는지 패턴을 찾을 수 있습니다.

의도와 목적

대시보드가 지금에 집중한다면, 이 화면은 전체 함대의 운영 품질을 다룹니다. 장비별 상태뿐 아니라 오류 빈도, 일정 준수율, 건전성 경고를 함께 보여, 반복되는 운영 리스크를 관리하려는 목적입니다.

고객이 얻는 것

  • 모든 AMR의 상태, 위치, 배터리, 작업을 표와 목록으로 비교해 병목, 유휴, 이상 장비를 한 번에 집계할 수 있습니다.
  • 일별 오류 건수, 시간 준수율 차트로 언제부터 나빠졌는지 추세를 확인하고, 원인 조사와 회의 자료로 활용할 수 있습니다.
  • 건전성 기준 미달, 점검 필요 장비를 따로 보여 사전 점검, 예방 정비 일정을 잡기 쉽습니다.
  • 특정 장비를 선택하면 개별 관제(SCR-03)로 바로 이어져, 탐색에서 조치까지 끊기지 않습니다.

목표: 개별 사고 대응을 넘어, 데이터로 운영 이상 구간과 취약 장비를 선제적으로 찾는다.

핵심 기능: AMR 목록, 오류/준수율 차트, 건전성 영역, 상태 테이블 | 구현: AmrListView, Analytics KPI API 일부 예정

4.5 페이지별 기능

SCR-03

AMR 개별 관제

문제가 난 한 대의 AMR에 집중해, 상태, 이력, 비상 조치를 한 화면에서 마칠 수 있습니다.

의도와 목적

통합 화면에서는 깊이 있는 판단과 즉각적인 통제가 어렵습니다. 이 화면은 이 로봇 한 대에 지금 무슨 일이 일어나고, 내가 무엇을 할 수 있는가에 답하기 위해 만들었습니다. 특히 비상 정지는 현장 안전과 가동 중단 범위를 좁히는 핵심 수단입니다.

고객이 얻는 것

  • 선택한 AMR의 작업, 배터리, 위치, 적재, SoH 등 운영에 필요한 정보를 모아, 현장 담당자와 같은 수준으로 상황을 공유할 수 있습니다.
  • 오류, 고장 코드가 있으면 무엇이 잘못됐는지 먼저 보이고, 대응 우선순위를 정할 수 있습니다.
  • 비상 정지 실행 시 시스템이 명령을 기록하고 시뮬/현장 동작을 멈추도록 하여, 멈췄다는 사실을 조직 전체가 같은 기준으로 확인할 수 있습니다.
  • 누적 주행, 시간 준수율 추이로 이 장비만의 운영 습관을 파악할 수 있습니다.

목표: 이상 징후 발견 후, 해당 AMR에 대한 확인, 정지, 보고까지 최소 단계로 완료한다.

핵심 기능: 장비 상세, 센서/상태, 비상 정지(E-Stop), 준수율 차트 | 구현: AmrDetailView, BE POST .../commands emergencyStop 완료

4.5 페이지별 기능

SCR-04

배터리 / 충전 스테이션 현황

충전 자원이 부족하거나 배터리가 바닥나기 전에 병목과 위험을 알 수 있습니다.

의도와 목적

AMR 물류는 움직일 수 있는 대수에 좌우됩니다. 충전소 점유, 대기열, 완충 예상 시간을 한곳에 모아, 가동 중단을 충전 문제로 막지 않으려는 화면입니다.

고객이 얻는 것

  • 스테이션별 연결, 충전 상태, 혼잡 여부를 보며 어느 충전소에 AMR을 보낼지, 대기를 어떻게 나눌지 결정할 수 있습니다.
  • 저전력, 충전 지연 알림으로 갑작스러운 정지, 작업 미이행을 줄일 수 있습니다.
  • 30분, 1시간, 그 이상 완충 예상 분포를 보며 당일 물류 계획을 현실적으로 조정할 수 있습니다.
  • 대기열에서 장비를 골라 개별 관제로 넘어가 충전 이슈와 운행 이슈를 연결해 볼 수 있습니다.

목표: 배터리, 충전 때문에 생산 라인이 멈추기 전에, 충전 운영을 재배치한다.

핵심 기능: 충전 요약 카드, 스테이션 상세, 대기열, 완료 예측 차트, 충전 알림 | 구현: ChargingStationsView, BatteryView 등

4.5 페이지별 기능

SCR-05

작업 이력 및 분석

지나간 작업과 이동 데이터를 숫자와 추이로 돌아보며, 다음 운영과 개선에 쓸 근거를 얻을 수 있습니다.

의도와 목적

실시간 관제만으로는 우리 물류가 실제로 얼마나 일했고, 어디가 비효율인지 설명하기 어렵습니다. 이 화면은 이력과 분석을 통해 보고, 공정 개선, 인력 배치, 레이아웃 검토에 필요한 운영 인사이트를 제공하려는 목적입니다.

고객이 얻는 것

  • 일별 작업 건수, 이동 거리, 작업 시간, 평균 처리 시간으로 생산성과 부하를 객관적으로 확인할 수 있습니다.
  • 시간대별, AMR별 작업 비중을 보며 피크 구간, 과부하 장비를 찾을 수 있습니다.
  • 작업 내역 목록(출발, 도착, 상태)으로 특정 사고, 지연의 전후 맥락을 추적할 수 있습니다.
  • 전일 대비 변화 등 요약으로 어제보다 나아졌는가를 짧은 회의에서 공유할 수 있습니다.

목표: 감에 의존하지 않고, 이동과 작업 데이터로 운영 개선과 의사결정을 뒷받침한다.

핵심 기능: 작업 요약 카드, 시간대/AMR별 차트, 작업 내역·일별 요약 테이블 | 구현: WorkHistoryView, Analytics/WorkHistory API

4.7 트러블슈팅 사례 ① 보안

jwt.secret 원격 커밋

무슨 일이 있었나

  • BE Security 설정 구현 중 Copilot이 application.yaml에 jwt.secret을 넣었습니다.
  • 로그인·토큰 서명에 쓰는 민감 키인데, 그대로 원격 저장소에 push되었습니다.

어떻게 발견했나

  • PR 생성 후 Copilot Review가 시크릿 포함을 지적했습니다.

조치

  • application.yaml을 공용 설정과 분리, jwt.secret은 로컬, 테스트 전용 파일에만 둠.
  • 해당 파일은 .gitignore에 추가해 원격에 올라가지 않게 함.

교훈: AI 생성 설정 파일은 커밋 전에 diff와 PR 리뷰로 반드시 확인합니다.

4.7 트러블슈팅 사례 ② 협업·리뷰

Copilot 리뷰 거부 (711 files)

무슨 일이 있었나

  • FE 작업 후 PR을 올리고 Copilot Review를 요청했습니다.
  • 변경 파일이 300개 이상이라 리뷰가 거부되었습니다.
  • dev merge 이력을 되돌려 재시도했으나, 여전히 거부되었습니다.

진짜 원인

  • 변경 목록을 보니 node_modules가 Git에 추적(tracked)되고 있었습니다.
  • .gitignore 누락으로 의존성 폴더 전체가 커밋에 포함된 상태였습니다.

조치 (해결 순서)

1

git rm -r --cached node_modules (로컬 폴더 삭제 불필요)

2

그 상태로 커밋 후 push (git add .로 다시 넣지 않기)

3

원격에서 node_modules 사라짐 확인 후 PR 리뷰 재요청 → 변경 약 49개로 감소

참고: 과거 커밋 이력에 남은 기록은 별도 정리가 필요합니다. 원격 트리에서는 추적 해제된 상태입니다.

4.7 트러블슈팅 사례 ③ 설계 정합

조치

  • 테이블, 컬럼명, 자료형을 API, 엔티티에 맞게 재정합.
  • BE 쪽 JPA 엔티티, DTO도 수정된 스키마에 다시 맞춤.
  • 이후 설계 변경은 docs/ 선행 수정 원칙을 팀에 공유.

교훈: 멀티 영역 병행 시 API, ERD, 화면을 주기적으로 교차 검토해야 합니다.
